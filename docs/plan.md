# SDVC 웹서비스 Codex 전환 — 구현 계획

2026-09-19 · 상태: **Plan·Tasks 승인 완료** · Analyze 보완 승인 완료 · Phase 1 착수

## 역할 매핑

| 제품 용어 | 기존 DB 역할 | 설명 |
|---|---|---|
| 수강생 | `developer` | 기존 계정·RLS·결제·프로젝트 소유권과 호환을 유지한다. 화면과 새 문서의 표시명만 수강생으로 통일한다. |
| 개발자/운영관리자 | `admin` + `admin_tier` | 수강생 현황·차단·감사 기능을 사용한다. 서버가 매 요청에서 역할과 등급을 확인한다. |

기존 `developer` 역할을 새 의미의 관리자 역할로 재사용하지 않는다. 향후 DB 역할명을 `learner`로 바꾸는 작업은 별도 호환성 마이그레이션으로 다룬다.

## 1. 구현할 결과

수강생이 브라우저에서 로그인하고 본인 OpenAI API 키를 등록하면, SDVC 문서를 AI와 작성하고 계획·작업 목록을 승인한 뒤 실제 서버·DB가 있는 웹앱을 생성한다. 서버는 실패 테스트 → 구현 → 재검증을 실제 실행하고, 검증된 버전을 고유 URL로 발행한다.

대표 결과물은 '방문자가 가입·로그인하고 자기 기록을 저장하는 독서 기록 웹앱'이다. 이름만 다른 정적 HTML이나 플랫폼의 기존 공통 records API를 연결한 예제로 완료 판정하지 않는다.

## 2. 기존 구현 재사용 및 변경

기준: pinusian/sdvc-app @ f361ca6be31d56016a1e0bd69c083dfebc1a75a3.

- 재사용 후보: Next.js 화면, Supabase 인증, 대화 UI, 프로젝트 목록, 첨부·사용량·관리자 기능의 필요한 부분.
- 교체: Anthropic 호출 및 관련 메시지 타입 → OpenAI 대화 어댑터와 Codex 코드 작업 어댑터.
- 강화: 대화 블록 승인 → 불변 문서 버전에 연결된 서버 승인.
- 추가: 사용자 OpenAI 키 보관, 코드 작업 환경, 실행 증거, 프로젝트별 DB·서버 배포.
- 교체: 파일 업로드 후 deployed 표시 → 테스트·빌드·배포 상태·URL 검증을 모두 확인한 published 상태.
- 신규 생성 앱은 관리 화면과 다른 origin에서 제공한다. 기존 /site 경로의 같은 출처 제공 방식을 신규 앱의 기본으로 사용하지 않는다.
- Stripe와 기존 Claude 방문자 AI 기능은 새 흐름의 의존성에서 분리한다. 실결제 확대는 이 계획에 포함하지 않는다.
- 수강생 로그인은 기존 Supabase Auth를 재사용하되, 로그인 성공만으로 권한을 확정하지 않고 서버가 활성·차단 상태를 매 요청마다 확인한다.
- 개발자 관리자 화면에는 수강생별 가입·최근 이용·프로젝트·실행·사용량·차단 상태를 제공한다. 관리자 역할은 서버 및 DB 정책으로 검증한다.
- 차단·해제는 사유 입력과 감사 기록을 필수로 하며, 차단 사용자의 새 AI 호출·프로젝트 변경·장시간 작업 재개를 서버에서 거부한다.

원본 방법론 저장소의 progress.md 및 제품 개요도 확인했다. 기존 교육 운영·배포 완료 기록은 참고 사실이며 이번 확장 범위의 승인·테스트 증거로 재사용하지 않는다.

## 3. 기술 구성과 이유

| 역할 | 선택안 | 선택 이유 |
|---|---|---|
| SDVC 서비스 화면·API | 기존 Next.js/TypeScript + Vercel | 기존 코드와 UI를 활용 |
| 플랫폼 인증·문서·작업·로그 | 플랫폼 전용 Supabase Auth/Postgres/Storage | 재접속 및 사용자별 접근 통제 |
| 문서 대화 | OpenAI 서버 API 어댑터 | 사용자 키를 서버에서 사용하고 구조화된 문서 저장 |
| 코드 작성·수정 | 서버 측 Codex SDK | 파일 작업·세션 재개를 코드로 제어 |
| 작업 지속·재시도 | Vercel Workflows | 브라우저 연결 종료와 장시간 작업 수명 분리 |
| 생성 코드 실행 | Vercel Sandbox | 운영 서비스와 격리된 환경에서 테스트·빌드 |
| 생성 앱 서버·URL | 앱별 Vercel 프로젝트 | Next.js 서버 API 실행 및 독립 배포 |
| 생성 앱 DB·방문자 인증 | 앱별 Supabase 프로젝트 | 수강생 앱끼리 및 플랫폼 DB와 분리 |

첫 버전 생성 스택은 Next.js/TypeScript와 Supabase로 한정한다. 서버는 Vercel에서 실행되는 앱별 API이며, 상시 동작하는 임의 서버·모든 언어를 지원한다는 뜻은 아니다.

앱별 Supabase 프로젝트는 격리가 명료하지만 생성 시간과 운영비가 증가한다. 인프라는 운영자 계정에서 관리하도록 제안한다. 수강생에게 Vercel·Supabase 가입을 추가로 요구하지 않는다. API 키 비용과 인프라 비용은 별개다.

## 4. 문서와 승인 상태

단계: constitution_specify → clarify → plan → tasks → analyze → implement → verify → publish → maintenance.

- documents: 종류·내용·버전·해시·작성 시각. 수정은 새 버전으로 저장한다.
- approvals: 사용자·프로젝트·문서 ID/해시·승인 시각. 승인 API는 서버가 실제 문서 및 현재 단계를 확인한다.
- 첫 실제 대화 요청에서 프로젝트 한도를 서버가 확인한 뒤 `draft` 프로젝트를 만들고 대화에 연결한다. 헌장·명세 단계부터 모든 문서는 이 프로젝트 ID에 결부한다. 대화만 만들고 메시지를 보내지 않은 경우에는 프로젝트를 만들지 않는다.
- 대화 어댑터는 블록별 구조화 문서 경계를 모델 출력에 요구하고 서버가 헌장·명세·명확화·계획·작업 문서로 분리한다. 필요한 문서가 빠졌거나 버전 저장이 실패하면 승인/다음 단계 게이트를 노출하지 않는다.
- plan/tasks 승인 없이 구현 요청은 거부한다. “예”라는 텍스트만으로 승인 기록을 만들지 않는다.
- 선행 문서 변경 시 영향받는 계획·작업 승인을 무효화한다. 실행 중 문서 변경은 현재 작업을 중단 또는 obsolete 처리하고 이전 결과를 새 승인본으로 발행하지 않는다.
- 단계 변경과 승인 저장은 DB 트랜잭션으로 묶고 예상 상태 버전을 비교한다. 중복 클릭은 같은 결과를 돌려준다.
- Analyze의 발견 사항은 보고서로 남기며 자동으로 승인 문서를 덮어쓰지 않는다.

### 세션 휴식과 재개

- `작업휴식`은 새 기능 작업을 중단하고 `docs/progress.md`를 갱신한 뒤 `.sdvc/session-checkpoint/`에 로컬 체크포인트를 만든다.
- 체크포인트에는 manifest, 진행 문서와 변경 중인 작은 텍스트 파일의 사본, working/staged patch를 저장한다. 원래 상대 경로와 SHA-256을 기록한다.
- `.env*`, API 키·토큰·인증 파일, 의존성, 빌드 결과, 대용량 바이너리는 제외한다. 체크포인트는 Git에 커밋하지 않는다.
- `SDVC 작동`은 체크포인트를 먼저 검사한다. 현재 파일이 사본과 같으면 `progress.md`의 다음 작업부터 바로 이어간다. 더 최신 변경이나 해시 오류가 있으면 자동 복원하지 않고 차이를 보고한다.
- 설치된 SDVC 스킬의 `scripts/session_checkpoint.ps1`을 Windows 저장·무결성 검사에 사용한다. 체크포인트는 같은 작업 공간에서 세션을 잇는 장치이며 다른 PC로 옮기는 백업은 아니다.
- 이 절의 `.sdvc` 체크포인트는 플랫폼 개발자의 로컬 Codex 작업용이다. 수강생이 브라우저를 닫았다 다시 접속하는 기능은 플랫폼 DB의 documents/approvals/runs/run_events를 읽어 복원한다.

기존 profiles/conversations/messages/projects를 활용하며 다음을 추가한다.

| artifacts / deployments | 불변 소스 버전, 배포 ID, URL, 검증 상태, 이전 정상 버전 |

API 경계: 로그인·로그아웃·세션 확인, 키 등록·상태·삭제, 문서 조회·수정·승인, run 생성·조회·이벤트·취소, 배포 조회·공개·이전 버전 전환, 관리자 수강생 현황·차단·해제. 모든 조작에서 플랫폼 사용자와 프로젝트 소유권 및 활성 상태를 확인한다. service-role을 쓰는 경로에는 소유권·관리자 역할·차단 우회 테스트를 별도로 둔다.

프로젝트 수 한도는 구현 파일이 처음 나온 시점이 아니라 첫 실제 대화에서 `draft` 프로젝트를 만들기 직전에 적용한다. 이후 같은 대화는 연결된 프로젝트를 재사용하여 중복 프로젝트·중복 한도 차감을 막는다.

## 6. API 키와 실행 격리

- 키 입력은 HTTPS로 서버에 한 번 전송한다. 조회는 등록 여부와 마스킹 정보만 반환한다.
- AES-GCM 등 인증 암호화와 버전 있는 서버 비밀값으로 암호화한다. 원문은 로그·문서·프롬프트·소스·워크플로 영속 입력에 넣지 않는다.
- Codex 제어 프로세스와 생성 코드를 실행하는 프로세스를 분리한다. 생성 앱 테스트 환경에는 사용자 OpenAI 원본 키와 운영자 Management API 토큰을 주지 않는다.
- Codex의 인증은 짧은 수명·사용자/실행 범위의 중계 자격과 서버 측 키 주입 방식으로 연결하는 안을 먼저 검증한다. 중계 경로·모델·요청량을 제한하고 원본 키를 반환하지 않는다.
- 이 중계 방식과 Codex SDK의 호환성은 아직 실증하지 않았다. 최초 기술 검증에서 실제 호출·스트리밍·키 차단을 확인하며, 실패하면 자격 증명을 생성 환경에 노출하는 우회 구현을 하지 않고 설계 변경안을 제시한다.
- Sandbox는 실행별 파일·네트워크를 제한한다. 플랫폼 DB 및 클라우드 관리 API 접근은 제어 서비스만 수행한다.
- 패키지 설치·빌드도 생성 코드 실행으로 취급한다. 운영 비밀값을 빌드 환경에 전달하지 않는다.
- 사용자 키 삭제 시 새 호출을 거부하고 진행 작업 취소 및 중계 자격 폐기를 요청한다. 이미 처리된 API 사용료까지 취소되는 것으로 표시하지 않는다.

## 7. 실제 TDD와 실행 증거

1. 승인된 요구에서 인수 테스트와 기능별 테스트를 작성하고 불변 테스트 묶음으로 보관한다.
2. RED: 테스트를 실제 실행한다. 환경 설정 오류나 테스트 0개 수집은 유효한 RED로 보지 않는다.
3. GREEN: 구현 후 같은 테스트 묶음으로 재실행한다. 테스트 삭제·skip·검증 약화로 성공시키지 못하도록 변경 내역을 확인한다.
4. REFACTOR: 정리 후 동일 테스트와 회귀 검사를 재실행한다.
5. 플랫폼이 관리하는 별도 인수 테스트로 인증·CRUD·권한·영속성·URL을 검증한다. 모델의 자기 보고만으로 합격시키지 않는다.

로그 수집은 신뢰하는 실행 제어 측이 수행한다. 시간·명령·종료 코드·코드/테스트 해시가 누락되면 미검증이다. 불안정한 테스트를 단순 반복해 통과 결과만 남기지 않는다. AI 생성 테스트 자체의 완전성을 보장한다고 주장하지 않는다.

## 8. DB 생성·배포·복구

- 운영자 Supabase 조직에 앱별 프로젝트를 준비하고, 관리용 자격은 제어 서비스에만 보관한다.
- 테스트는 격리 환경의 임시 Postgres/Supabase 환경에서 수행하고, Auth/RLS를 포함한 통합 검증은 운영 데이터가 없는 별도 검증 리소스에서 수행한다. 필요한 실행 이미지와 DB 호환성을 기술 검증에서 확인한다.
- 생성 앱의 migration은 버전 관리하며, 최초 빈 DB에 검증된 migration을 적용한다. 테스트에 운영 DB를 사용하지 않는다.
- 앱 배포에는 그 앱에 필요한 자격만 등록한다. 서버 전용 비밀과 공개 Supabase 키를 구분한다.
- 불변 소스 버전을 Vercel 배포 API에 넘기고 READY를 확인한다. 배포 ID 획득만으로 완료 처리하지 않는다.
- 로그인 화면·서버 health·DB CRUD·자기 데이터 격리를 실제 URL에서 확인한 후 안정 URL을 새 버전으로 전환한다.
- 실패·취소·재시도 때 기존 정상 배포를 유지하고, idempotency key 및 외부 리소스 ID로 중복 생성·중복 청구를 줄인다.
- 코드 롤백과 DB 롤백은 구분한다. 코드 버전 변경이 DB 데이터를 되돌리지 않는다. 기본은 이전 코드와 호환되는 추가형 migration이며 데이터 삭제·비호환 migration에는 영향과 복구 방안을 별도 제시한다.
- 부분 생성된 리소스는 orphan 상태로 기록하고 운영자가 확인할 수 있게 한다. 사용자 데이터가 있는 DB를 실패 처리만으로 자동 삭제하지 않는다.

## 9. 화면

1. 로그인/가입.
2. AI 연결 설정: OpenAI 키 등록·교체·삭제·오류 및 비용 안내.
3. 프로젝트 목록: 단계, 최근 실행, 결과물 URL.
4. 작업 공간: 단계 표시, 대화, 문서 보기·버전·승인 버튼.
5. 구현 화면: 기능별 진행, RED/GREEN 증거, 취소·재시도.
6. 결과 화면: 고유 URL, 검증 상태, 배포 이력, 수정 요청.
7. 세션 상태: 최근 체크포인트 시각, 재개 가능 여부, 충돌 또는 무결성 오류.
8. 개발자 관리자 화면: 수강생 검색·이용 현황·최근 활동·차단 상태·차단/해제 및 감사 기록.

제품 화면에는 인프라 내부 용어 대신 '테스트 실행 중', '데이터 저장소 준비 중', '결과물 공개 중'처럼 사용자가 판단할 수 있는 상태를 표시한다.

## 10. 비용과 운영 설정

- OpenAI 사용료: 수강생 본인의 API 계정에 청구. ChatGPT 구독과 별개.
- Sandbox/Workflow/배포/DB/저장소 비용: 제안 구조에서는 운영자 부담. 사용자 API 키만으로 충당되지 않는다.
- 초기 설정 제안: 사용자당 동시 실행 1개, 서비스 전체 동시 실행 2개, 자동 수정 최대 3회, 작업 시간 상한 20분. 수치는 운영자가 변경 가능한 제품 보호 한도이며 공급자의 한도라고 주장하지 않는다.
- 외부 유료 리소스 생성 전에 운영자가 금액 예산과 프로젝트 상한을 설정하도록 한다. 가격·플랜·쿼터는 실제 계정에서 확인하며 무료 운영을 보장하지 않는다.
- 개발·시험은 별도 Vercel 프로젝트와 Supabase 리소스를 사용한다. 기존 sdvc-app 운영 DB에 먼저 migration을 적용하지 않는다.
- 운영자 필요 설정: Vercel 팀/배포 권한, Sandbox/Workflow 이용 가능 여부, Supabase 조직/관리 권한, 플랫폼 DB, 암호화 비밀값. 값은 관리 UI 또는 환경변수에 직접 입력한다.

## 11. 구현 순서와 검증 전략

이 절은 설계 순서이며 승인 전 tasks.md를 만들지 않는다.

먼저 가장 위험한 경로를 기술 검증한다: 사용자 키 중계 → Codex 파일 변경 → 별도 환경의 실제 테스트 실패/성공 → DB 준비 → Vercel 배포 → URL 확인. 각 공급자의 어댑터를 분리해 실패 지점을 확인한다.

이후 수강생 인증·차단 경계, 개발자 이용현황·차단 관리, 키 등록, 버전 문서와 승인, 지속 작업, 전체 TDD 실행, DB·배포 자동화, 브라우저 통합을 사용자 기능 단위로 구현한다. 플랫폼 코드도 RED → GREEN → REFACTOR로 개발한다.

검증은 Vitest 단위·계약 검사, PostgreSQL 권한/트랜잭션 통합 검사, Playwright 사용자 시나리오, lint·type/build 검사 및 실제 공급자 연동 검증으로 구성한다. 모의 어댑터만 통과한 상태를 실제 서비스 완료로 보고하지 않는다.

개발자는 로컬에서 플랫폼과 모의 공급자로 개발할 수 있다. 실제 생성·DB·배포 검증에는 계정 설정과 네트워크가 필요하다. 수강생의 이용에는 로컬 개발 환경이 필요 없다.

## 12. 헌장 점검 및 승인 대상

- 설치 없음: 수강생은 브라우저와 본인 API 키만 사용.
- 방법론 준수: 서버 상태·버전 승인·읽기 전용 분석.
- TDD: 실제 실행 기록과 별도 인수 테스트.
- URL: 실제 서버·DB를 포함한 배포 후 검증.
- 보안: 사용자 키 암호화, 실행 격리, 앱별 DB/배포.
- 기록: 문서·실행·배포 연결 및 progress.md.

승인 대상은 위 범위, 표준 생성 스택, 앱별 DB/배포, 운영자 인프라 비용 구조, 기술 검증 후 기능 구현 순서다. 사용자는 수강생 로그인, 개발자 이용현황 화면, 악성 수강생 차단 기능을 조건으로 2026-09-19 승인했다. 기술 검증에서 핵심 가정이 실패하면 영향과 수정 계획을 먼저 제시한다.
